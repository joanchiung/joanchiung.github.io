## A reskin request, a rebuild problem

FIDO2 verification was a standalone backend service. This verification UI was built directly into the backend service's codebase early in development, by a backend engineer, without ever aligning with the main app's frontend standards. The result was a visual mismatch.

Since this system serves an industry that depends heavily on trust and rigor, every screen needs a consistent visual language. With the verification pages living outside the main app, every adjustment required cross-team coordination and carried a high maintenance cost. The PM's original request was a visual reskin: just make the styling match the main app.

After taking over and reviewing the backend service's code, a simple reskin turned out to be impossible. The frontend was plain static `.html`, sharing no components or style system with the main app. Users also reached the page through fixed links generated by an external system, so making the URL change invisible to users meant touching not just the visuals but the routing and verification logic underneath. The real goal was to bring the entire frontend into the frontend monorepo and rewrite it in Next.js, integrated with the main app. The PM asked for a reskin. What actually needed rebuilding was the skeleton underneath.

## The old URLs can't change

The registration links generated by the old service use fixed static `.html` filenames, for example:

```
/verify/register.html?token=<one-time token>
```

This URL is an interface already hardcoded by an external system, used to generate the QR code users scan. Any change would ripple through every external integration, so it can't be changed unilaterally.

A redirect won't work here, because a redirect changes the URL bar to the new path, so users and external systems would see a different address than before, which directly violates the requirement that users must never notice the URL changed. To swap the underlying implementation without leaving a trace, the only option is a rewrite, mapping the old URL to the new route:

```ts
rewrites.push({ source: '/verify/register.html', destination: '/verify/register' });
rewrites.push({ source: '/verify/authenticate.html', destination: '/verify/authenticate' });
```

The URL bar stays the same, while the new page actually renders underneath. This mapping stays in place indefinitely, since the external naming is fixed and won't change. It isn't a temporary shim to drop once migration is done.

## Middleware has to let these URLs through

FIDO verification never required login in the first place. Anyone with the link should be able to see the verification page, since the device doing the QR code scan never carries a session.

The main app has a layer of middleware that checks login status on every request and redirects to the login page if there's no session. Paths that don't require login are registered in a whitelist, marking `/verify/register` and `/verify/authenticate` as accessible without login.

The whitelist needs to cover both layers of the path, not just the new post-migration path. The reason lies in the order Next.js processes a request:

```
headers → redirects → middleware → rewrites → dynamic routes
```

Middleware runs before rewrites, so it always checks the raw URL the user actually requested, not the path after the rewrite. If the whitelist only registers the new path (`/verify/register`), middleware is actually checking the raw pre-migration URL (`/verify/register.html`). The two don't match, so the request gets blocked as if it required login. A separate whitelist covering the raw paths is needed:

```ts
const UNAUTHORIZED_RAW_ROUTES = [
  '/verify/register.html',
  '/verify/authenticate.html',
];

function isUnauthorizedRoute(pathname: string): boolean {
  if (UNAUTHORIZED_RAW_ROUTES.includes(pathname)) return true;
  return UNAUTHORIZED_ROUTES.some((route) => matchesRoutePattern(pathname, route));
}
```

Put together, the full flow looks like this:

```
Scan QR code
  → hits /verify/register.html?token=...
    → middleware checks (sees the pre-migration path)
        ├─ in the RAW whitelist → allowed through
        │     → rewrite: register.html → /verify/register
        │         → new page renders
        └─ not in the whitelist → redirected to /login (shouldn't happen)
```

## The deploy is where it broke

The code worked fine locally, but after deploying to the develop environment, the new page never showed up.

The old verification page hadn't been decommissioned, and was still serving callers that hadn't switched over yet. With the old and new interfaces sharing the same path, the system had no way to tell which side should handle a given request. Before the frontend moved into the monorepo, requests to these verification paths only had one destination, so no distinction was needed. After the move, requests under the same path prefix had to split into two routes: requests for the page itself go to the new frontend, while the actual verification API requests still go to wherever the backend logic lives.

This routing split was a requirement created by the migration itself; it didn't exist before. I had no visibility into the backend code, so I couldn't tell which service the problem was in, and could only hand the observed symptoms (where it stalled, when it happened) to the backend team to investigate together. It turned out the routing rules simply weren't pointing at the new service's location. Once that was fixed, old and new each resolved to the right place, and the frontend side didn't need any further changes: it just started rendering correctly.

## Outcome

With the verification flow now maintained inside the main app, users no longer get bounced out to a separate system, and the experience reads as one consistent product. Adjusting the verification logic going forward no longer requires cross-team coordination either. It's a single place to change.

The main app already carries a lot of functionality, and the verification flow should keep users focused on verification itself, not distracted by unrelated interface details. Working with the PM, design, and backend, I aligned the FIDO pages around that principle, keeping only what the verification task actually needs.

The lesson from this project: before splitting one service into two, you need to think through exactly how to divide whatever they used to share, in this case, routing. Problems that stay invisible while everything is combined only surface once you pull it apart.
